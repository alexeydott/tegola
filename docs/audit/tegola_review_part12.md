## 0. Проход 4: полный аудит текущей ветки

### Методика прохода 4

* Четыре параллельных аудита по областям: PostGIS/HANA; MySQL/GPKG; codec/CRS/MOS/EPSG; server/cache/cmd/atlas/env.
* Ручная перепроверка каждой ключевой находки чтением кода. Спорные находки субагентов удалены или понижены (пример: предполагаемая гонка в реестре proj, см. 0.6).
* Сверка с upstream master через raw.githubusercontent.com (gcs.go, hana/util.go, middleware_gzip.go, middleware_tile_cache.go, internal/env/parse.go).
* Ограничения: `go.mod` и `internal/build` не индексируются поиском. Тесты не запускались, анализ статический.

Легенда:

* Приоритет: **P1** (исправить до релиза), **P2** (исправить в ближайшей волне), **P3** (долг, гигиена).
* Происхождение: **форк** (код или поведение введены в форке) или **upstream** (унаследовано, в upstream master так же).
* Достоверность: **подтверждено** (код прочитан), **вероятно**, **нужна проверка в рантайме**, **не перепроверено** (только отчет субагента).

### 0.3 Новые находки P1

#### N1. Блокировка метатайла сериализует попадания в кэш (P1, форк, подтверждено)

* Где: `server/middleware_tile_cache.go:66–101`; координатор `server/handle_map_layer_zxy.go:63–108`.
* Что: `TileCacheHandler` вызывает `tileUpdateLocks.acquire(metatileLockKeyForCacheKey(key))` с `defer unlock()` **до** `cacher.Get`. Блокировка держится до конца обработчика: при попадании включает `w.Write(cachedTile)`, при промахе включает `next.ServeHTTP` (рендер тайла) и `cacher.Set`.
* Upstream: в `TileCacheHandler` нет никакой блокировки, `cacher.Get` вызывается напрямую.
* Сценарий: веб-карта запрашивает 10–30 соседних тайлов. Большинство тайлов одного зума попадают в один метатайл 8x8, поэтому все запросы идут строго по очереди. Один медленный клиент (медленная сеть при отдаче из кэша) или один медленный рендер блокирует все остальные тайлы метатайла. На горячих зумах параллелизм падает почти до 1.
* Дополнительно: `acquire` использует `lock.mu.Lock()` без учета `r.Context()`. Отключившиеся клиенты остаются в очереди и затем выполняют ненужный рендер. Очередь не ограничена, поэтому число горутин растет без предела.
* Причина: комментарий в `:62–65` объясняет цель: не дать старому рендеру перезаписать свежий результат `?tile=update`. Цель верная, но блокировка покрывает слишком много.
* Исправление:
  1. Путь попадания (`Get` + отдача) выполнять без блокировки.
  2. Для промаха использовать `singleflight` по ключу тайла, чтобы параллельные промахи одного тайла рендерились один раз.
  3. Защиту от устаревшей записи делать через счетчик поколений метатайла: запомнить поколение перед рендером, перед `Set` сравнить под короткой блокировкой; если поколение изменилось, не писать в кэш.
  4. В координаторе ждать блокировку через канал-семафор с `select` по `ctx.Done()`.
* Тесты: параллельные попадания в один метатайл не ждут друг друга; отмененный контекст освобождает очередь; `?tile=update` во время рендера промаха не перезаписывается старыми байтами.

#### N2. Операции изменения кэша без аутентификации (P1, форк, подтверждено)

* Где: `server/handle_map_layer_zxy.go:254–273`, `333–345`, `359–465`; `server/middleware_tile_cache.go:40–54`.
* Что: любой клиент на публичном маршруте тайлов может вызвать `?tile=update` или `?tile=getupdated`. Сервер перекодирует и записывает в кэш до 64 тайлов метатайла под блокировкой N1. `?dirty` (и `?dirty=1`, `?dirty=true`) принудительно регенерирует тайл и перезаписывает кэш. Нет аутентификации, нет лимита частоты, нет переключателя в конфигурации (поиск по `config/`, `server/`, `cmd/` не нашел ни одного флага).
* Upstream: middleware пропускает любые запросы с query-параметрами мимо кэша; операций изменения кэша через HTTP нет.
* Сценарий: скрипт перебирает `z/x/y?tile=update`. Каждый запрос делает 64 рендера и 64 записи, держит блокировку метатайла и через N1 блокирует обычных пользователей. Это прямой DoS базы и хранилища кэша.
* Исправление:
  1. Добавить флаг конфигурации (например, `webserver.tile_operations`), по умолчанию выключен. При выключенном флаге `?tile=` и `?dirty` игнорировать или отвечать 403.
  2. При включенном флаге требовать токен (заголовок) или отдельный admin-listener.
  3. Ограничить частоту и число одновременных операций обновления.
* Тесты: без флага `?tile=update` не вызывает `Set`; без токена ответ 403.

### 0.4 Новые находки P2

#### N5. Пустой hostname ломает старт (P2, форк, регрессия, подтверждено)

* Где: `internal/env/parse.go:346–351` (`parseHostName`: пустая строка -> ошибка «hostname: value is empty»), вызов из `internal/env/types.go:171–185` (`URL.UnmarshalTOML`), поле `config/config.go:76`.
* Upstream: `ParseURL` вызывает `url.Parse(val)`, пустая строка дает пустой URL без ошибки. `cmd/tegola/cmd/server.go:44–47` задает `server.HostName` только при `Host != ""`, иначе сервер берет хост из запроса.
* Сценарий: `hostname = ""` или `hostname = "${TEGOLA_HOSTNAME}"`, где переменная задана пустой строкой (типично для Docker/Helm шаблонов). В upstream это «использовать хост запроса». В форке это фатальная ошибка конфигурации. Неустановленная переменная дает `ErrEnvVar` и в upstream, и в форке, это не регрессия.
* Тесты: `types_test.go` покрывает только `nil`, пустую строку не покрывает.
* Исправление: в `ParseURL` после `replaceEnvVar` и `TrimSpace` возвращать `nil, nil` для пустого значения. Добавить тесты для `""`, `"   "` и пустой env-переменной.
* Нужна проверка в рантайме: IPv6 `[::1]` и `[::1]:8080` в ветке `url.Parse("//" + s)`.

#### N6. GPKG raw-таблицы игнорируют настроенные bbox-поля (P2, форк, подтверждено)

* Где: `provider/gpkg/gpkg_register.go:743–759`, `detectBoundColumns` `:313–330`, `rawBoundsSQL` `provider/gpkg/gpkg.go:146–166`.
* Что: `detectBoundColumns(colNames)` знает только фиксированные `minx/maxx/miny/maxy`. Настроенные `bbox_*_fieldname` попадают только в `layer.bboxFields` и только если автодетекция вернула nil. `rawBoundsSQL` читает только `boundFieldnames`. Поэтому настроенные имена никогда не дают SQL-фильтр, и каждый тайл сканирует всю таблицу. Комментарий `:748–750` («configured bbox_\*_fieldname values win») противоречит коду.
* Исправление: если все четыре настроенных столбца есть в `colNames`, записывать их в `boundFieldnames`. Настроенные имена должны иметь приоритет над автодетекцией. Добавить тест с нестандартными именами bounds и проверкой, что SQL содержит фильтр.

#### N7. Интерполяция строк в SQL PostGIS (P2, форк, подтверждено)

* Где: `provider/postgis/postgis.go:448–460` (`inferTableSRID`: `fmt.Sprintf("SELECT Find_SRID('%v', '%v', '%v')", ...)`), `splitTableName` `:429–440`, MapplGIS-проба `:577–580` (`FROM %v."%v"`).
* Что: значения из конфигурации вставляются без экранирования. `splitTableName` делит по первой точке и не понимает кавычки (`"my.schema"."t"`). Источник значений: конфигурация оператора, поэтому это в первую очередь баг корректности (имена с `'`, `"`, `.`), а не удаленная инъекция. Генерация кавычек для полей в `postgis/util.go:79–101` не удваивает внутренние `"` (не перепроверено).
* Исправление: `SELECT Find_SRID($1, $2, $3)` с аргументами; идентификаторы через `pgx.Identifier{schema, table}.Sanitize()`; разбор имени через `parse_ident()` на стороне БД или парсер с учетом кавычек. Тесты с именами, содержащими `'`, `"` и точку.

#### N8. MySQL: SRID слоя из одной строки (P2, форк, вероятно)

* Где: `provider/mysql/register.go:484–503` (`SELECT geom ... LIMIT 1`).
* Что: если SRID не задан явно, SRID из заголовка одной случайной строки становится SRID слоя. В таблице со смешанными SRID фильтр `!BBOX!` и перепроецирование будут неверны для части строк без предупреждения.
* Исправление: проверять `SELECT DISTINCT ST_SRID(geom) ... LIMIT 2`; если значений больше одного, завершать регистрацию с ошибкой и советом задать `srid`/`crs_defn` (как уже сделано для PostGIS в `docs/crs.md`).

#### N10. HANA: `rows` не закрываются (P2, upstream, подтверждено)

* Где: `provider/hana/util.go:127–151` (`getLayerFields`, вызов `getLayerRows` в `:140`). В upstream master так же.
* Сценарий: каждая регистрация слоя без `fields` держит соединение. При множестве слоев пул исчерпывается.
* Исправление: `defer rows.Close()` сразу после проверки ошибки. Кандидат в upstream PR.

#### N11. HANA: плейсхолдер `$1` (P2, upstream, нужна проверка в рантайме)

* Где: `provider/hana/util.go:83` (`isSrsRoundEarth`, `$1`), рядом `hasSrsPlanarEquivalent` `:76` использует `?`. Ошибка отбрасывается через `_ =`. Вызов: `hana.go:717–718`.
* Риск: если go-hdb не принимает `$1`, функция всегда возвращает false для SRID, отличных от 4326, и ветка round-earth не срабатывает. Upstream идентичен.
* Исправление: заменить на `?`, возвращать ошибку. Кандидат в upstream PR.

#### N12. HANA: `quoteIdentifier` пропускает сырой ввод (P2, upstream, подтверждено)

* Где: `provider/hana/util.go:47–52`. Если строка начинается с `"`, она возвращается без проверки. `"a"; DROP ...` проходит как есть. Источник значений: конфигурация. Upstream идентичен.
* Исправление: разбирать quoted identifier до закрывающей кавычки с учетом `""`, отклонять хвост.

#### N13. WKB-декодер: выделение памяти по счетчику из данных (P2, upstream, подтверждено)

* Где: `third_party/go-spatial/geom/encoding/wkb/internal/decode/decode.go:53–59, 77–84, 97+, 143–153`: `make(..., num)`, где `num` это uint32 из потока.
* Сценарий: одна поврежденная строка с `num = 0xFFFFFFFF` вызывает попытку выделить десятки ГБ и OOM процесса. Форк более уязвим, потому что добавил raw-форматы `wkb` (MySQL, GPKG, PostGIS, HANA), где данные не проходят проверку СУБД.
* Исправление: перед `make` проверять `num * минимальный_размер_элемента <= оставшиеся_байты`, иначе ошибка. Тест-фаззер на `DecodeBytes`. Кандидат в upstream PR (go-spatial/geom).

#### N14. gzip-декомпрессия ответа (P2/P3, upstream, подтверждено)

* Где: `server/middleware_gzip.go:136–156`.
* Что: `gzipDecompressResponseWriter.Write` создает новый `gzip.NewReader` на каждый вызов `Write`. Тело, записанное за несколько вызовов, не декодируется. Метод возвращает `len(b)` сжатых байт, а не число записанных. `Content-Length` удаляется и не выставляется, ответ идет chunked.
* Upstream: тоже reader на каждый `Write`; `Content-Length` выставлялся после тела и не действовал.
* Исправление: буферизовать сжатое тело целиком и распаковывать при завершении обработчика, затем выставить `Content-Length`. Тест с телом, записанным частями.

#### R1. PostGIS и HANA не используют общую подготовку пробы (P2, форк, подтверждено)

* Где: PostGIS `inspectMOSLayerGeomType` `postgis.go:684–688`: `strings.Replace(l.sql, "!ZOOM!", ..., 1)` и `!BBOX!` -> `TRUE`; мертвый `args` `:694`. HANA `hana.go:955` и `:1039`: `!ZOOM!` заменяется один раз.
* Сценарий: SQL с двумя `!ZOOM!` оставляет второй токен в пробе, проба падает. `!BBOX!` внутри функции (`ST_Intersects(geom, !BBOX!)`) превращается в `ST_Intersects(geom, TRUE)`, проба падает.
* Исправление: перевести обе пробы на `codec.PrepareProbeSQL` / `WrapProbeSQL`, как MySQL (`register.go:540–548`). Удалить мертвый `args`.

### 0.5 Новые находки P3

* **N3 (форк, подтверждено).** `status.updating` вводит в заблуждение. `locked()` (`handle_map_layer_zxy.go:101–107`) возвращает true при `refs > 0`, а refs считает и обычные запросы middleware (N1). Значит «updating» истинно при любом обычном запросе в метатайле. Исправление: отдельный счетчик именно для операций `?tile=update`.
* **N4 (форк, подтверждено).** Обновление метатайла кодирует и кэширует тайлы вне границ карты. Проверка границ (`handle_map_layer_zxy.go:222–247`) применяется только к запрошенному тайлу. Исправление: фильтровать все 64 тайла по границам карты до рендера.
* **N9 (форк, подтверждено).** `mysql/register.go:407`: `layerConf.String(ConfigKeyTableName, &idFieldname)` передает `idFieldname` как значение по умолчанию для `tablename`. Сейчас безвредно, потому что ключ проверен ранее, но это ошибка копирования.
* **N15 (upstream, подтверждено).** `gpkg/gpkg.go:75–89` `decodeGeometry` не проверяет флаг пустой геометрии заголовка. `IsGeometryEmpty` (`binary_header.go:192–197`) используется только в тестах. Пустые геометрии идут в WKB-декодер.
* **N16 (upstream, подтверждено).** `maths/webmercator/pseudo.go:22–40` `PLatToY` молча превращает NaN (|lat| > 90) в 0. Некорректные координаты рисуются на экваторе. Исправление: ограничивать широту ±85.0511 или возвращать ошибку.
* **N17 (форк, подтверждено).** `basic/epsg.go:178–190`: синтетические SRID выдаются атомарным счетчиком, поэтому один и тот же `crs_defn` получает разный SRID в разных процессах и при другом порядке загрузки. Если SRID попадает в ключи кэша, логи или внешние системы, это ломает согласованность. Исправление: детерминированный SRID от хэша нормализованного определения (в диапазоне >= 340000001) с разрешением коллизий.

* Совет: гонка регистрации маршрутов — не только тестовая проблема: она может проявиться и на проде при медленном старте.

#### 7.1.2. Постгрес-зонд нейтрализует `!BBOX!` значением `TRUE` до подстановки bounds-предиката

* Где: `provider/postgis/postgis.go:955` (`probeMOSCustomSQLContract`: `strings.ReplaceAll(sql, conf.BboxToken, "TRUE")`).
* Что: для MOS custom SQL валидация требует токен `!BBOX!` (`RequireBBoxCustomSQL`). Зонд заменяет его на `TRUE` (убирая фильтр), затем вызывает `replaceTokens`, который подставляет bounds-предикат в `!BBOX!`. Но токен уже заменен на `TRUE` — итоговый SQL зонда не содержит bounds-фильтра вовсе. Для зонда это не фатально (сэмпл читается без фильтра, LIMIT 16), но семантика расходится с gpkg/mysql, где зонд строится из permissive-инспекции с `1=1`. Риск: если `replaceTokens` оставит неверифицированный SQL (например, при синтаксической ошибке), зонд проверит не тот запрос, что задуман.
* Путь решения: привести к единому порядку, как в gpkg/mysql: сначала `replaceTokens` (подстановка bounds-предиката с расширенным extent), затем нейтрализация/выполнение. Либо осознанно документировать: зонд выполняет SQL без spatial-фильтра.
* Совет: закрепите выбранный порядок в `InspectSQLGeometryContract` контрактом «зонд всегда получает SQL без !BBOX!-фильтра» и одним тестом на провайдер.

#### 7.1.3. MySQL-зонд для формата `auto` считает декодируемые строки MOS-валидными без проверки MOS-подписи

* Где: `provider/mysql/register.go:596–616` (ветка `layerGeometryFormat == GeometryFormatAuto`), `provider/mysql/mysql.go:153–216` (`decodeGeometry` для `auto`).
* Что: зонд для `auto` вызывает `decodeGeometry(value, "auto", ...)`, который для `auto` принимает MySQL-нативную геометрию, WKB и даже WKT. Любая декодируемая строка засчитывается как «валидная MOS-строка». Итог: обычная таблица с нативной геометрией + bounds-колонками (например, MINX/MAXX/MINY/MAXY как бизнес-атрибуты) будет ошибочно помечена `MapplGISSQLSample`, а формат принудительно переключен на `mos`. В(gpkg-ветке зонда этой проблемы нет: зонд выполняется только для явного `FormatMOS`.)
* Путь решения: в decode-callback зонда для `auto` требовать явную MOS-подпись (`mos.IsSystemInfoBlob` уже существует как фильтр — нужен аналог для MOS-геометрии, или сначала проверять заголовок MOS-блоба). Тегированание `MapplGISSQLSample` и принудительный перевод `auto -> mos` только при положительной MOS-подписи.
* Совет: это ошибка ложного срабатывания (false positive) — самая опасная категория для авто-детекции, потому что молча меняет формат слоя. Добавьте регрессионный тест: таблица с нативной геометрией и колонками MINX/MAXX/MINY/MAXY не должна детектироваться как MapplGIS.

#### 7.1.4. Хронометраж вероятной регрессии: плоское экранирование `pgQuoteIdent` в stdSQL (`"geom" &&`)

* Где: `provider/postgis/util.go:145`: `sqlTmpl = 'SELECT %[1]v FROM %[2]v WHERE ST_SetSRID("%[3]v",0) && ' + config.BboxToken`.
* Что: для синтетических SRID геометрия в stdSQL оборачивается `ST_SetSRID("geom",0)`. Ранее (проход 1) генерируемый SQL строился как `WHERE "%[3]v" && !BBOX!`. Новое экранирование добавляет двойные кавычки — в Postgres это case-sensitive идентификатор. Если колонка создана без кавычек (`geom` в нижнем регистре), поведение не меняется; но колонки в смешанном регистре без кавычек (созданные без экранирования и приведенные к нижнему регистру) продолжат работать. Риск меньше, чем кажется: идентификаторы в шаблоне — фиксированное имя колонки из конфига, и `pgQuoteIdent` экранирует вложенные кавычки корректно. Пункт понижен до «проверить»: прогнать тест на слое с колонкой в смешанном регистре.
* Путь решения: регрессионный тест на tablename-слой с колонкой `Geom` (смешанный регистр, созданной с кавычками).
* Совет: квотирование идентификаторов — правильное направление; проверка только в одном кейсе смешанного регистра.
